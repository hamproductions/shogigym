# 局面別コーチ発話のサンプル調査

## 調査方法

本調査は、平手初期局面からローカルエンジンと合法手選択で作る合成対局を対象とする。人間の実戦棋譜ではない。ランダム性を含む着手選択で局面を分散させ、保存した棋譜・SFEN・解析結果を再生可能な根拠とする。短時間探索を使うため、解析値は確定的な棋理判定ではない。

発話はこのセッションのモデル／サブエージェントが作る実例であり、100MBモデル、WebLLM、Jev、外部APIの出力ではない。実装、モデル比較、音声品質、実時間レイテンシの評価には用いない。外部推論API・音声生成は呼び出していない。

## 根拠と文章を分ける規則

- 実着手、王手、駒取り、成り、駒打ち、持駒は局面の前後から検証する。
- 利きの存在と合法な駒取りを区別する。「取れる」には合法な指し手が必要。
- エンジンPVは一つの参考手順。「必ず」「受けがない」「強制」は全応手の検証なしでは使わない。
- 評価値の符号は先後と手番を固定する。短時間解析の値を実際の勝率や勝敗確定に置換しない。
- 「新たに守る／斜線を開く」などの因果表現には前後の利きの差が必要。
- 実際の続行、解析上の応手、改善候補を明示的に区別する。
- 根拠IDを発話に添えて追跡する。ただしIDがあるだけで正しい説明とは判定しない。
- 推奨手を隠す問題状態では、発話や矢印から解答を漏らさない。

## 成果物

生成結果とサンプルを以下に保存した。

- `games.json`：合成対局と終了理由。
- `facts.json`：選択した局面と解析・観測根拠。
- `samples.json`：根拠付きの短い発話と詳しい説明。
- `verification.json`：独立した合法手再生と観測値の再計算。

## パイロットで現れた説明の型

最初の4対局は固定した4手の開始列と100ms探索を用いたパイロット。329手、選択22局面。選択局面には駒取り8、成り1、駒打ち9、王手2、飛角香系の利き情報8を含む。同じ局面が複数項目に該当する。対局全体の頻度推定ではなく、選択した教材候補の構成である。

| 型                 | 必要な入力                       | 文章の骨格                                   | 誤りやすい解釈                               |
| ------------------ | -------------------------------- | -------------------------------------------- | -------------------------------------------- |
| 駒取りと取り返し   | 実際の捕獲、次手の合法捕獲       | 駒を取った後に、移動した駒へ取る手が残る     | 一手の捕獲をそのまま最終的な駒得にする       |
| 駒打ちと持駒       | 打った種類、打つ前後の枚数       | 持駒を盤上へ使い、残り枚数が変化             | 駒打ちを捕獲や素材増加と扱う                 |
| 斜線・縦横の利き   | 移動元・先、遮断駒、前後の利き   | どの升まで利きが届くかを具体的に示す         | 幾何学的な利きを合法な駒取りや勝ち筋と断定   |
| 既存の脅威が残る   | 着手前後の同じ関係と合法応手     | 動かした駒とは別の、残った注意点を示す       | 着手が原因で脅威が新しく生じたと説明         |
| 成りと捕獲後の形   | 捕獲・成り・手に入る駒・取り返し | 昇格と持駒増加を区別し、応手を確認           | 大駒を取って成ったという見栄えだけで成功扱い |
| 静かな一手         | 実着手と現在の持駒・配置         | 観測できる変化を短く述べる、または発話を省く | 根拠のない囲い・構想・玉の安全度を創作       |
| 条件付きの参考手順 | 開始SFENと合法PV                 | 例えばこの応手なら、次にこう進む             | 相手が必ずその順を選ぶと表現                 |
| 詰みの終局         | 王手と全合法応手の不在           | この局面は詰みと明確に伝える                 | resignやmate値だけで詰みと判定               |

### 発話選択への示唆

駒取りだけに反応するより、取り返し・持駒・次手を組にした方が具体的な助言になる。一方、単に金が上がった局面へ毎回長い説明を付けると、根拠を越えた構想の創作が増える。重要な変化だけ短く話し、参考手順は要求時に展開する方針を検討する。

同じ型へ異なる駒・升を挿入できる。今回の候補文からは、観測事実を伝える部分の多くを小さなテンプレート集合で表現できる可能性がある。LLMの効果として別に検証すべきなのは、複数の事実から何を優先するか、説明の分かりやすさ、キャラクター表現、繰り返しの抑制。22局面の試作だけで、LLMが不要または小型モデルで十分とは結論しない。

短文と詳細は解答の露出を別々に分類する。実着手後の説明でも、合法な次手を明示する文章はクイズのヒントになるため、問題表示では抑制する。音声も同じ露出判定に従う。

### 解析データを文章へ渡す前の問題

MultiPVの最新順位別ログは、探索途中の異なる更新時点を含み、最終bestmoveと順位1のPVが一致しない場合が実際にあった。最終bestmoveと同じ初手を持つ候補を明示的に対応付け、見つからない場合は評価値をnullにした。短いPVと評価値だけで自然な説明を生成する前に、こうしたデータの整合性を確保する必要がある。

## ランダム開始・棋力設定の追加対局

パイロットは開始列も探索時間もランダムではなかった。追加対局ではエンジンが実際に公開するSkillLevel設定と、合法な候補からの開始12手の乱択を使った。設定値、種、終了理由、解析条件は追加対局のJSONに保存した。パイロットの文章を追加対局の生成結果として扱わない。

## ガイドの分類と発話の分類

ガイドの既存分類は変更しない。`categories.json` は150教材のメタデータを、既存の分類関数と対応させた索引。本文の再監査や全教材の音声対応完了を意味しない。定跡は教材グループに加え、37種類の戦法選択を別に持つ。

| ガイドの大分類         | 説明の主眼                                 | 発話の組み立て                                     |
| ---------------------- | ------------------------------------------ | -------------------------------------------------- |
| はじめての将棋         | 何が変わったか、どのルール・一手先を見るか | 一つの事実 → 見る場所 → 確認の問い                 |
| 上達のためのテクニック | 利き・取り返し・守備・逃げ道の比較         | 具体的な関係 → 合法な応手 → 比較する一点           |
| 定跡                   | 選んだ戦法の局面と手順の意味               | 本線との関係 → 今の配置で成立する理由 → 分岐・移行 |

カテゴリとは別に、局面イベント、発話の目的、根拠の強さ、解答の露出を持たせる。例えば同じ角取りでも、ルールの案内は「馬を取ると持駒では角に戻る」、手筋の案内は「取り返す駒を三種類比較する」、定跡の案内は「選択した角交換の手順と照合する」となる。定跡の説明だけは、角を交換したという事実に加えて該当する教材・手順の根拠が必要。

### 選択する順序

1. 王手・終局・反則等、優先する事実を確定する。
2. 学習中なら選択中のガイド分類・教材・戦法を取得する。自由対局では認識できた範囲だけを使い、不明な戦法名は付けない。
3. 対応するカテゴリの型と、必要なら戦法固有の型を絞る。
4. 型ごとの必須根拠がそろった候補だけを残す。足りなければ、根拠がそろう基本の型を使うか発話しない。
5. 一つの主要な説明を選び、必要な升・駒・手順を埋める。音声、文、盤上表示は同じ根拠を参照する。
6. 確認・ヒント・解答後の検討を分ける。同じ局面を何度も説明しない。

この絞り込みなら、小型分類器やJevに渡す選択肢は関連する数種類に限定できる。自然文の生成までLLMに担当させる場合も、全パターン集を毎回入力する必要はない。これは実装案であり、精度・速度・費用の実測ではない。

### 実例とテンプレートの区別

`randomized/SAMPLES.md` は実際のローカルエンジン対局に対応する24例。パターン集の `{piece}` 等は未充填の設計用スロットであり、追加の実戦例ではない。sampleIdsは原則として仕組みの実例との対応で、戦法や囲いの認識が検証済みという意味にはしない。今回のランダム対局だけで全ての囲い・定跡を網羅したとは扱わない。

配置変化と短い合法手順の説明は確認できたが、守備駒を外して必ず崩せること、逃げ道を全て塞ぐ強制手順、詰めろ・必至、特定戦法の正しい分岐判定などは別の根拠が必要。それぞれのパターンに必要条件と未取得の例を残す。

## 最終成果物と確認結果

- [ガイド別パターン集](PATTERN_CATALOG.md)：3大分類と21の教材グループ、設定のみの3見出し、戦法選択のみの角交換振り飛車を区別する。37戦法の固有パターンと共通の型を合成し、112パターンを定義した。
- [ランダム対局の24発話例](randomized/SAMPLES.md)：盤面・手駒・実着手・条件付きの参考順から作った、短文と詳細の実例。
- [分類の対応表](coverage.json)：既存150単位の所属と37戦法の選択肢を照合し、各グループに必要な型があることを確認。14パターンに機構の実例を付けた。残りは未取得として残し、名前の一致だけで棋譜を割り当てていない。
- [ランダム対局の独立検証](randomized/verification.json)：全実着手・全保存PVの合法再生、持駒・盤上数、取りの証拠、評価視点、開始候補・SkillLevel、全終局の確認。
- [発話の追加確認](randomized/semantic-verification.json)：24文の本文を根拠と照合し、64件の追加確認を実行。取り返し時に誰の持角が増えるかの曖昧さを修正した。

### カテゴリ設計から得られたこと

ルールは移動・駒打ち・成りを分け、入門は一手の獲得と取り返しの比較に絞る。手筋は利きの増減・二標的・短い応手列を別の型にする。囲い崩しは守備駒の除去・侵入口・退路、囲いは守備の増減・玉の通り道・攻守の優先を分ける。寄せは王手への受け、実局面の詰み、条件付きの脅威を分ける。

定跡では、同じ飛車移動でも相掛かりの引き場所、石田流の横道、四間飛車の遮断駒、向かい飛車の対向する二枚の間、右四間の銀との集中など、見る関係を変える。名称は根拠ではなく、どの関係を優先して確かめるかの文脈になる。

持駒へ入るときは成りを戻すため、「取った駒」と「手に入った駒」を別スロットにした。テンプレートの肯定・否定・変化の意味まで照合し、欄が埋まっただけで発話を許可しない。これが、小型モデルに表現を任せる前にコード側で保持するべき情報である。

112は設計した型の数であって、112種類の実戦検証、全定跡の認識成功、音声対応、小型モデルの合格を意味しない。今回は例文と設計資料を完成させた段階で、製品への接続は行っていない。
